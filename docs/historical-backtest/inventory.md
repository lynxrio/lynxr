# Historical data feasibility and timestamp coverage

Repository-source audit on 2026-11-20, based on main `95c3e2c`. **A real January 2025 reconstruction is not established.** No production queries, private backups, real creator payloads, scraping, model calls or generated-script evaluation were performed. Schema capability is not evidence that qualifying records exist.

The count was not independently queried. The fresh checkout contains zero tracked CSV/JSONL/Parquet files and zero tracked `data/` or `output/` paths (`git ls-tree -r --name-only HEAD`). [README.md](../../README.md) describes the ignored master CSV and raw-part directories. Tracked showcase assets are a selected marketing sample, not a historical population.

Existing backups may be a future audit lead, not authorized research data. [backup_supabase.py](../../pipeline/backup_supabase.py) writes a run timestamp, table counts/bytes, skipped tables and exclusions in `MANIFEST.json`. A backup capture time can establish that a value existed **by that backup**, if its provenance is authentic; it cannot establish that an overwritten count was known in January 2025. No backup files or manifests were opened. A metadata-only manifest would still need private permission review before use.

## Historical reliability classes

Classify each *field/observation* separately, then require all mandatory fields of a record to qualify. Do not upgrade a record because one timestamp looks plausible.

- **A — archived, attested:** authentic publication, discovery, collection, observation and availability records with matching metric definitions and age; known population and permission. Eligible only after the cutoff checks. No real records assigned A here.
- **B — publication known, measurement current/unknown:** can describe historical publication, cannot supply cutoff engagement or follower counts. Typical current master/table risk.
- **C — derived/inferred:** taxonomy, transcript analysis, format vectors and reach tiers. Retain source provenance, model/version, fitting population and extraction/availability times; never present as measured platform evidence. Eligibility requires the chosen research arm to permit them.
- **D — missing/conflicting/unauthorized:** absent clocks, conflicting identities, hidden counters converted to zero, unclear rights, unavailable media. Keep the exclusion or unknown reason; do not reconstruct missing history.
- **S — synthetic:** all bundled fixtures and output in this PR. Invented timestamps, IDs, structural labels, permission flags and outcomes validate software mechanics only.

## Bias and unsuccessful-video feasibility

Retrospective discovery of both successful and unsuccessful posts is **not demonstrated**. Existing hashtag/relevance searches, curated source choices, selected creator panels, capped latest results, omitted pinned posts and available-only URLs are not a complete historical listing frame. Deleted low performers can be absent before collection; high performers may remain visible longer. Missing/hidden values converted to zero can also create false failures. Different platforms expose different counters, so cross-platform pooling would add measurement bias.

The next permitted analysis should audit a fixed, cutoff-defined panel's metadata manifest for all eligible posts, including removed/private/unmeasured entries and original inclusion probabilities. Census all posts in the frozen window; report the denominator at listing, feature availability, age-valid outcome and baseline stages. Missingness must be stratified by creator and source, with attrition sensitivity rather than imputed failure. A separate oversampled failure diagnostic set needs strata/weights and cannot supply unweighted population precision or lift. The prototype rejects non-census probabilities.

Current tracking is a candidate **future** collection mechanism, not authorization to collect. A separately approved prospective plan would preserve collection/availability provenance, actual observation ages, stable listing denominators and documented deletion/retention rules. If authentic 2025 archives cannot be supplied, the January question remains unanswered; no new scraping is proposed in this PR.

## Existing evaluation reuse and limits

[eval_scripts.py](../../pipeline/eval_scripts.py) provides the existing entry point. Its legacy paths import production modules and can read backups or spend money; this PR adds an early `historical` branch before those imports and directory creation. Only bundled synthetic files are accepted. PR #10's isolation pattern and synthetic-evidence separation were reviewed and reused conceptually; its unmerged branch is not changed, copied wholesale or made a dependency. Its script-craft detectors cannot establish historical discovery or future performance.

[post_match.py](../../pipeline/post_match.py) attributes a creator's published post to their own generated branded script using lexical/identity guards. Its scores are not reusable-format equivalence thresholds. [hook_views.py](../../pipeline/hook_views.py) supplies an existing precedent for same-creator/age normalization, leave-other-post baselines and creator resampling, but its full-library day-7–10 analysis is not an as-of forecast. Calling it unfiltered would risk future-post baselines. The new stdlib-only module separates history, frozen prediction, candidate matching and outcomes; it does not call either production reader.

No evidence here answers whether Lynxr could have generated effective scripts in 2025. That requires separately defined, blinded structural-fidelity and creator editing-burden evaluation, and a clear modern-model versus historical-system distinction. See [design](design.md) for frozen matching, baseline metrics, walk-forward controls and provisional product dependencies.
